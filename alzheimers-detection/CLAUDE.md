# CLAUDE.md

Guidance for Claude Code (or any Claude instance) working in this repository.
Read this fully before making changes — several conventions here exist
because of medical-safety and data-licensing requirements, not just style
preference.

## What this project is

An open-source **digital biomarker research/screening-support platform**
for early cognitive decline (Alzheimer's/MCI research). It is explicitly
**not** a diagnostic tool and must never be made to claim otherwise — see
"Hard rules" below before touching any user-facing text.

Origin: this repo started from an ambitious brief (15 cognitive test
instruments, 5 sensing modalities, multimodal fusion, "FDA-ready"). The
deliberate engineering decision was to build one modality end-to-end and
tested rather than stub everything shallowly. See `docs/ARCHITECTURE.md`
for the full reasoning — don't re-litigate this without reading it first.

## Hard rules (do not violate these, even if asked)

1. **No gated dataset ever gets committed.** DementiaBank/Pitt Corpus,
   ADReSS/ADReSSo, ADNI, or any other access-controlled corpus content
   (`.cha` files, raw audio, transcripts) must never appear in this repo.
   `.gitignore` blocks the obvious cases (`data/`, `*.cha`) but review
   diffs yourself too. See `docs/DATASETS.md` for exactly what's
   real/available/gated — don't invent new "public" datasets not listed
   there without verifying (search the web) that they're actually real
   and actually accessible the way you claim.
2. **No diagnostic-claim language.** Nothing in this codebase may state or
   imply a diagnosis ("you have Alzheimer's", "positive for dementia",
   etc.). All user-facing disclaimer/result text goes through
   `core/disclaimers.py` — don't write disclaimer copy inline.
   `tests/test_no_diagnostic_language.py` is a CI floor, not a substitute
   for judgment on new copy.
3. **No "FDA-ready" claims.** That's a regulatory/clinical-validation
   process, not a code deliverable. Don't let README/docs drift toward
   implying regulatory clearance that hasn't happened.
4. **Optional heavy deps degrade soft, not hard.** `faster-whisper`,
   `parselmouth`, `spacy` are all lazy-imported with a clear
   `ImportError` message naming the install extra. Follow this pattern for
   any new heavy dependency (CV models for a future drawing/handwriting
   modality, etc.) — the core test suite must never require a GPU or a
   multi-hundred-MB model download.
5. **New model-derived numbers need a citation or an explicit "unvalidated
   placeholder" label.** See `_REFERENCE_RANGES` in `speech/pipeline.py`
   and `docs/BIOMARKERS.md` for the pattern. Don't ship invented thresholds
   as if they were clinically validated.

## Commands

```bash
# Install (editable, with dev + speech extras)
pip install -e ".[dev,speech]"

# Run the fast test suite (no gated data, no real model downloads)
pytest -m "not slow"

# Lint / type check (both run in CI)
ruff check src tests
mypy src

# Run the API locally
uvicorn alzheimers_detection.api.main:app --reload
# docs at http://localhost:8000/docs

# Full stack via Docker
docker compose up --build
```

## Known environment caveat from prior sessions

The sandbox this project was originally built in had **no network access**,
so FastAPI/Pydantic/SQLAlchemy/etc. could not actually be `pip install`ed
or executed there — all verification of that code was syntax-checking
(`py_compile`) plus manually re-deriving test math in bare Python (numpy
was pre-installed) to hand-check expected values. That process did catch
and fix three real test bugs (wrong word/utterance counts, a tokenizer/
fixture mismatch). Point being: **run the real test suite yourself** in
whatever environment Claude Code has network access from — treat anything
untested-by-execution in this repo's history as "logic-reviewed, not
CI-verified" until you've actually run `pytest` green.

## Conventions to follow when extending

- Pydantic models (data contracts) live in a `schemas.py` per package
  (`speech/schemas.py`; a `core/schemas_auth.py` or similar for auth —
  not yet created).
- Feature extraction functions should be pure where possible (input data
  in, dict/model out) for easy unit testing without mocking — see
  `acoustic_features.extract_timing_features` as the pattern.
- Any new modality follows the `speech/` structural pattern:
  `schemas.py` → extraction module(s) → `pipeline.py` (orchestration +
  explainability + limitations list) → `api/routes/`. See
  `CONTRIBUTING.md` "Adding a new modality" section.
- Config lives only in `core/config.py`, env-prefixed `ALZDX_`, accessed
  via the cached `get_settings()`, never `Settings()` directly.
